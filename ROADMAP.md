## Notes on sequencing

- **Phase 4 depends on Phase 3**, not just Phase 1, because a player needs at least one real, approved venue with courts to book against — building the player flow against pure mock data risks schema drift from the venue-owner flow. Build venue owner core first, seed one approved venue, then build player flow against real data.
- **PWA work (Phase 5) is deliberately last before deployment**, not first. Wrapping unfinished screens in a service worker early creates cache-invalidation debugging overhead for no benefit — do it once the screens are stable.
- **Nothing in Phases 0–5 depends on Hostinger being reachable.** Local dev against a Convex dev deployment works standalone; Hostinger only enters the picture at Phase 6. Don't let Hostinger account/FTP setup block earlier phases — that's why it's scoped to Phase 0 as "access confirmed" only (not full deploy pipeline).
- **Phase 8 exists to close gaps found on review, not to add scope.** Tasks 13–15 fix real debt (routing, admin bootstrap, timezone correctness) identified while independently verifying Phases 2 and 7 — none of them were required to make the app *work*, but all three would be more expensive to fix after Hostinger deploy than before it. Task 16 is pure documentation and has zero risk of blocking anything; it exists so Task 11/12a criterion 4 can be executed quickly the moment Hostinger credentials arrive, instead of being figured out live. Do Task 13 first (routing touches the most surface area); 14 and 15 can happen in either order; 16 last.
- **Phase 9 is presentation-layer only, deliberately separated from Phase 8's structural work.** Every Convex function, role check, and double-booking guard verified in Phases 1–7 is untouched by Phase 9 — its tasks (17–21) explicitly forbid touching `convex/*.ts` logic, keeping the risk profile low even though it touches nearly every screen. Do Task 17 (shared primitives) first, since 18–20 all consume it; touching every form/list twice (once without primitives, once to retrofit them) is wasted work. Task 20 specifically should wait for Phase 8's Task 13 if that hasn't landed yet, since both touch the same dashboard panel files — check current state before starting rather than guessing which order causes less rework. Task 21 (accessibility/responsive audit) is last because it audits the *outcome* of 17–20.
- **Phase 10 touches `convex/*.ts` again, unlike Phase 9 — treat it with the same rigor as Phases 1–7, not Phase 8/9's lighter cleanup review.** Task 23 in particular adds a new atomicity-sensitive check (court blocks) to the existing booking mutation R-4 already governs — this is exactly the kind of change CLAUDE.md's review checklist item 2 (verify a real negative test, not just UI hiding) and item 4 (does this touch a BLOCKING risk) exist for. Do Task 23 first since Task 24's bookings view and the availability display both benefit from blocks being modeled; 24 and 25 can happen in either order after that; Task 26 (suspension) is independent and can happen anytime, but doing it last means its role-check changes only need to be threaded through the codebase once.
